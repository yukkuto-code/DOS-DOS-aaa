# yukkuto-code.github.io — 負荷テスト・サンドボックス

元のページは、任意の URL を入力すると **毎秒最大 10 万件の GET 要求を、同時 200 並列で送り続ける** ものでした。

このバージョンは **URL を自由に指定できる元の形式に戻しつつ、速度と総量に上限を入れた** ものです。対象は自分が管理するサーバー、または管理者の許可を得たサーバーを想定しています。

---

## 1. 元の形式との違い

| 項目 | 元の実装 | この実装 |
| --- | --- | --- |
| 対象 URL | 任意に入力できる | **同じ（任意に入力できる）** |
| 送信レート | 毎秒 1〜100,000 件 | **最短 500 ms 間隔 = 毎秒 2 件まで** |
| 同時接続 | 200 | **1** |
| 1 回の総量 | 無制限 | **100 件** |
| 継続時間 | 停止するまで無限 | **3 分で自動終了** |
| レート制御 | なし | 毎分 120 件・同一ホスト 1 セッション 200 件 |
| 応答の扱い | `no-cors` で読まずに盲撃ち | 必ず読み、3 回連続失敗で停止 |
| 失敗時の挙動 | 無視して送り続ける | 記録して打ち切り |
| 入力検証 | なし | http/https のみ、認証情報入り URL は拒否 |
| 外部依存 | CDN の Bootstrap + インライン onclick | ゼロ（自前 CSS/JS、CSP、`textContent` のみ） |
| 既定の動作 | いきなり送信 | シミュレーション（送信 0 件） |

元の「任意 URL を指定できる」という使い勝手はそのまま残しました。変えたのは **速さと量** です。

## 2. なぜレート上限が「安全性」なのか

負荷試験ツールと DoS ツールの違いは、機能ではなく **レートと総量** です。

* 毎秒 2 件・1 回 100 件・同時 1 本では、相手のサーバーに実質的な負荷はかかりません。1 本のブラウザタブで人間が F5 を連打するのと同程度です。
* 一方、毎秒 100,000 件・並列 200 本は、1 台の端末で現実のサービスを落とせる量です。ここが分水嶺で、この版はその手前に固定しています。
* 応答を必ず読むので、相手が既に苦しければ 3 回で止まります。盲撃ちをしません。

### 上限の実装

```js
const SAFETY = Object.freeze({
  MAX_REQUESTS_PER_RUN: 100,
  MIN_INTERVAL_MS: 500,          // = 最大 2 req/s
  CONCURRENCY: 1,
  MAX_REQUESTS_PER_MINUTE: 120,
  SESSION_CAP_PER_ORIGIN: 200,
  MAX_RUN_MS: 180000,
  TIMEOUT_MS: 3000,
  MAX_CONSECUTIVE_ERRORS: 3,
});
```

* `Object.freeze` 済み。実行中に書き換えても反映されません。
* 入力値は必ず `clamp()` を通します（`budgetNumber` に 99999 を入れても 100 になります）。
* 上限を UI から引き上げる入力欄は存在しません。

## 3. 使い方

### 3.1 対象サーバーを立てる

CORS ヘッダが必要です（ブラウザから応答を読むため）。`probe_server.py` が自動で付与します。

```bash
python3 probe_server.py --port 8000
# -> http://127.0.0.1:8000/
#    確認用: /__stats__ で受信件数を確認できる
```

すでに自分のサーバーがある場合は、`Access-Control-Allow-Origin` を返すようにしてください。nginx なら:

```nginx
add_header Access-Control-Allow-Origin "*" always;
```

### 3.2 ページを開く

```bash
python3 -m http.server 8123 -d .
# -> http://localhost:8123/index.html
```

1. 「測定対象」に対象 URL を入れて **この URL を使う**
2. モードを **セルフ計測** に切り替え
3. 管理者チェックと `TEST` を入力
4. 間隔（500 ms〜5 s）と回数（1〜100）を決めて **開始**

### 3.3 つまずきやすい点

| 症状 | 原因と対処 |
| --- | --- |
| 3 回で止まる | 到達不能 / ポート違い / CORS ヘッダ不足。ログにヒントが出ます |
| `TypeError` になる | 同上。`curl -I` で対象が応答するか、CORS ヘッダがあるか確認 |
| https ページから http 対象へ送れない | mixed content。`localhost` / `127.0.0.1` 以外は仕様上不可。ページを http で開く |
| リダイレクトで失敗する | `redirect: 'error'` のため。最終 URL を直接指定する |
| 200 件で止まる | 同一ホストのセッション上限。ページを再読み込みするとリセットされます |

## 4. 安全性の担保箇所

1. **レートと総量** — 上記の定数。最大でも毎秒 2 件・1 回 100 件。
2. **送信経路は 1 箇所** — `probeOnce()` のみ。ここで「実行開始時の対象と一致するか」を毎回検査します。
3. **応答を読む** — `no-cors` を使わない。`credentials: 'omit'`、`redirect: 'error'`、`referrerPolicy: 'no-referrer'`。
4. **入力検証** — http/https のみ。`user:pass@` を含む URL は拒否。
5. **CSP** — `default-src 'none'; connect-src 'self' http: https:`。外部スクリプトの読み込みは不可。
6. **DOM** — `textContent` のみ。`innerHTML` / `eval` / `new Function` 不使用。インラインイベントハンドラなし。
7. **タブ非表示で停止** — `visibilitychange` で打ち切り。
8. **iframe 内で動作しない** — クリックジャッキング対策（`frame-ancestors` は `<meta>` では無効なため JS で代替）。
9. **既定はシミュレーション** — 開いた直後に押しても 1 バイトも送信しません。

## 6. 検証したこと

ヘッドレス Chromium による自動テスト。

| 検査 | 結果 |
| --- | --- |
| 既定の対象 | `assets/ping.txt` / バッジ「同梱」 |
| `ftp://` を入力 | 「http:// または https:// のみ」で拒否、対象は不変 |
| `http://user:pass@host/` | 認証情報入りとして拒否 |
| 壊れた文字列 | 形式エラーで拒否 |
| 任意の URL を指定 | バッジが「指定」に変わり、その URL が対象になる |
| 管理者チェックなしで開始 | ブロック（送信 0） |
| 実測 4 回 / 500 ms | 4 件成功、対象サーバー側の受信も 4 件、所要 1.7 秒 |
| 実測 100 回 / 500 ms | 100 件成功、対象サーバー側の受信も 100 件、所要 50 秒 |
| 到達不能な対象 | 3 回連続失敗で自動停止、ヒントを表示 |
| 回数に 99999 を入力 | 100 にクランプ |
| 言語切替 | ログ・状態表示とも追従して再翻訳（「完了」表示も維持） |
| コンソールエラー | 到達不能テスト時のみ（意図的） |

## 7. 運用上の注意

* 第三者のサーバーに負荷をかける行為は、日本では不正アクセス禁止法や偽計業務妨害の評価対象になり得ます。国によってはコンピュータ・ミスユース法違反です。**許可を得た対象だけ** に使ってください。
* このページを公開ホストに置く場合、誰でも「自分のサイト」を測れてしまいます。上限が低いので実害は小さいですが、身内用なら **アクセス制限（Basic 認証や Cloudflare Access）** をかけるのが無難です。
* より本格的な計測が必要なら、k6 / wrk / ab などサーバー側から実行するツールの方が正確です。ブラウザ経由の計測は CORS と mixed content の制約を受けます。
