# yukkuto-code.github.io — 負荷テスト・サンドボックス

元のページは、任意の URL を入力すると **毎秒最大 10 万件の GET 要求を、同時 200 並列で送り続ける** ものでした。

このバージョンは **URL を自由に指定できる元の形式に戻しつつ、速度と総量に上限を入れた** ものです。対象は自分が管理するサーバー、または管理者の許可を得たサーバーを想定しています。

---

## 1. 元の形式との違い

| 項目 | 元の実装 | この実装 |
| --- | --- | --- |
| 対象 URL | 任意に入力できる | **同じ（任意に入力できる）** |
| 送信レート | 毎秒 1〜100,000 件 | **最短 500 ms 間隔 = 毎秒 2 件まで** |
| 同時接続 | 200 | **1** |
| 1 回の総量 | 無制限 | **100 件** |
| 継続時間 | 停止するまで無限 | **3 分で自動終了** |
| レート制御 | なし | 毎分 120 件・同一ホスト 1 セッション 200 件 |
| 応答の扱い | `no-cors` で読まずに盲撃ち | 必ず読み、3 回連続失敗で停止 |
| 失敗時の挙動 | 無視して送り続ける | 記録して打ち切り |
| 入力検証 | なし | http/https のみ、認証情報入り URL は拒否 |
| 外部依存 | CDN の Bootstrap + インライン onclick | ゼロ（自前 CSS/JS、CSP、`textContent` のみ） |
| 既定の動作 | いきなり送信 | シミュレーション（送信 0 件） |

元の「任意 URL を指定できる」という使い勝手はそのまま残しました。変えたのは **速さと量** です。

## 2. なぜレート上限が「安全性」なのか

負荷試験ツールと DoS ツールの違いは、機能ではなく **レートと総量** です。

* 毎秒 2 件・1 回 100 件・同時 1 本では、相手のサーバーに実質的な負荷はかかりません。1 本のブラウザタブで人間が F5 を連打するのと同程度です。
* 一方、毎秒 100,000 件・並列 200 本は、1 台の端末で現実のサービスを落とせる量です。ここが分水嶺で、この版はその手前に固定しています。
* 応答を必ず読むので、相手が既に苦しければ 3 回で止まります。盲撃ちをしません。

### 上限の実装

```js
const SAFETY = Object.freeze({
  MAX_REQUESTS_PER_RUN: 100,
  MIN_INTERVAL_MS: 500,          // = 最大 2 req/s
  CONCURRENCY: 1,
  MAX_REQUESTS_PER_MINUTE: 120,
  SESSION_CAP_PER_ORIGIN: 200,
  MAX_RUN_MS: 180000,
  TIMEOUT_MS: 3000,
  MAX_CONSECUTIVE_ERRORS: 3,
});
```

* `Object.freeze` 済み。実行中に書き換えても反映されません。
* 入力値は必ず `clamp()` を通します（`budgetNumber` に 99999 を入れても 100 になります）。
* 上限を UI から引き上げる入力欄は存在しません。

## 3. 使い方

### 3.1 対象サーバーを立てる

CORS ヘッダが必要です（ブラウザから応答を読むため）。`probe_server.py` が自動で付与します。

```bash
python3 probe_server.py --port 8000
# -> http://127.0.0.1:8000/
#    確認用: /__stats__ で受信件数を確認できる
```

すでに自分のサーバーがある場合は、`Access-Control-Allow-Origin` を返すようにしてください。nginx なら:

```nginx
add_header Access-Control-Allow-Origin "*" always;
```

### 3.2 ページを開く

```bash
python3 serve.py --port 8123
# -> http://localhost:8123/index.html
```

`serve.py` は GitHub Pages と同じ 404 の返し方（404 ステータス ＋ `404.html`）をするため、存在しない URL の確認もこれ 1 本で済みます。中身は静的ファイルの配信だけなので、`python3 -m http.server 8123 -d .` でも画面自体は動きます（ただし 404 の挙動は再現されません）。

1. 「測定対象」に対象 URL を入れて **この URL を使う**
2. モードを **セルフ計測** に切り替え
3. 管理者チェックと `TEST` を入力
4. 間隔（500 ms〜5 s）と回数（1〜100）を決めて **開始**

### 3.3 つまずきやすい点

| 症状 | 原因と対処 |
| --- | --- |
| 3 回で止まる | 到達不能 / ポート違い / CORS ヘッダ不足。ログにヒントが出ます |
| `TypeError` になる | 同上。`curl -I` で対象が応答するか、CORS ヘッダがあるか確認 |
| https ページから http 対象へ送れない | mixed content。`localhost` / `127.0.0.1` 以外は仕様上不可。ページを http で開く |
| リダイレクトで失敗する | `redirect: 'error'` のため。最終 URL を直接指定する |
| 200 件で止まる | 同一ホストのセッション上限。ページを再読み込みするとリセットされます |

## 4. 安全性の担保箇所

1. **レートと総量** — 上記の定数。最大でも毎秒 2 件・1 回 100 件。
2. **送信経路は 1 箇所** — `probeOnce()` のみ。ここで「実行開始時の対象と一致するか」を毎回検査します。
3. **応答を読む** — `no-cors` を使わない。`credentials: 'omit'`、`redirect: 'error'`、`referrerPolicy: 'no-referrer'`。
4. **入力検証** — http/https のみ。`user:pass@` を含む URL は拒否。
5. **CSP** — `default-src 'none'; connect-src 'self' http: https:`。外部スクリプトの読み込みは不可。
6. **DOM** — `textContent` のみ。`innerHTML` / `eval` / `new Function` 不使用。インラインイベントハンドラなし。
7. **タブ非表示で停止** — `visibilitychange` で打ち切り。
8. **iframe 内で動作しない** — クリックジャッキング対策（`frame-ancestors` は `<meta>` では無効なため JS で代替）。
9. **既定はシミュレーション** — 開いた直後に押しても 1 バイトも送信しません。

## 6. 存在しない URL の扱い（404）

**html 以外のパスも、存在しないページも、同じ扱い** にしました。

| アクセス先 | ステータス | 画面 |
| --- | --- | --- |
| `/` または `/index.html` | 200 | 通常の画面 |
| `/styles.css`、`/app.js`、`/assets/ping.txt` | 200 | 実ファイル（画面を成立させるため必要） |
| `/foo`（拡張子なし） | **404** | 404 画面 → 自動で `index.html` へ |
| `/index`、`/index.htm`（別拡張子） | **404** | 404 画面 → 自動で `index.html` へ |
| `/foo/bar.html`（存在しないパス） | **404** | 404 画面 → 自動で `index.html` へ |
| `/assets/`（`index.html` の無いディレクトリ） | **404** | 404 画面 → 自動で `index.html` へ |

ポイントは **ステータスを 200 に化けさせない** ことです。存在しない URL は 404 のまま返し、その応答本文（`404.html`）の中で `location.replace()` を使って `index.html` に戻します。リダイレクトで 302 を返す実装にすると「存在しない URL が 200/302 で通る」状態になり、検索エンジンや監視からは正常ページに見えてしまいます。

### 6.1 `404.html` の中身

* GitHub Pages は、実ファイルの無いパスに対して **`404.html` を 404 ステータスで** 返します（この動きはサーバー側の仕様なので、こちらで設定するものはありません）。
* 戻り先は状況に応じて決めます。ドメイン直下の配信（`https://<user>.github.io/`）なら `/index.html`、プロジェクトページ（`/repo/`）なら `/repo/index.html` を、`HEAD` で存在確認してから選びます。
* 戻り先が無い場合の **無限ループは 3 秒のクールダウンで打ち切ります**（`sessionStorage` に最終遷移時刻を記録）。打ち切ったときは「自動で戻れませんでした」と表示し、手動リンクだけ残します。
* JavaScript が無効な環境でも `<noscript>` の `meta refresh` で戻ります。
* `<meta name="robots" content="noindex, nofollow">` を付け、404 ページ自体は索引させません。

### 6.2 ローカルで確かめる

GitHub Pages と同じ判定をする小さなサーバーを同梱しました（標準ライブラリのみ）。

```bash
python3 serve.py --port 8123
# -> http://127.0.0.1:8123/index.html   200
# -> http://127.0.0.1:8123/nope         404 + 404.html（そのまま index.html へ戻る）
```

`python3 -m http.server` では `404.html` が使われないため、この確認には使えません（標準の 404 文言が出ます）。

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8123/index.html   # 200
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8123/nope         # 404
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8123/index        # 404
```

## 7. 検証したこと

ヘッドレス Chromium による自動テスト。

| 検査 | 結果 |
| --- | --- |
| 既定の対象 | `assets/ping.txt` / バッジ「同梱」 |
| `ftp://` を入力 | 「http:// または https:// のみ」で拒否、対象は不変 |
| `http://user:pass@host/` | 認証情報入りとして拒否 |
| 壊れた文字列 | 形式エラーで拒否 |
| 任意の URL を指定 | バッジが「指定」に変わり、その URL が対象になる |
| 管理者チェックなしで開始 | ブロック（送信 0） |
| 実測 4 回 / 500 ms | 4 件成功、対象サーバー側の受信も 4 件、所要 1.7 秒 |
| 実測 100 回 / 500 ms | 100 件成功、対象サーバー側の受信も 100 件、所要 50 秒 |
| 到達不能な対象 | 3 回連続失敗で自動停止、ヒントを表示 |
| 回数に 99999 を入力 | 100 にクランプ |
| 言語切替 | ログ・状態表示とも追従して再翻訳（「完了」表示も維持） |
| コンソールエラー | 到達不能テスト時のみ（意図的） |
| 実測 2 回 → 履歴 2 件、前回と自動比較 | 2 件・差分表が出る |
| リロード後も履歴が残る | 残る |
| 11 件で「10 回ごと」 | 2 グループ（1–10 / 11–11） |
| 区切りを 5 に変更 | 3 グループ |
| 「日時で分ける」 | 今日 / 直近 7 日 / 直近 30 日 / それ以前 |
| ホスト絞り込み | 該当ホストの行だけになる |
| シミュレーション実行 | 履歴に追加されない |
| 履歴を消す | 0 件になり空表示に戻る |
| `/nope`（存在しない） | 404 ＋ `404.html` → `/index.html` に着地 |
| `/index`（拡張子なし） | 404 ＋ `404.html` → `/index.html` に着地 |
| `/index.htm`（別拡張子） | 404 ＋ `404.html` → `/index.html` に着地 |
| `/assets/`（`index.html` の無いディレクトリ） | 404 ＋ `404.html` → `/index.html` に着地 |
| `/styles.css` `/app.js` `/assets/ping.txt` | 200（画面を成立させる実ファイル） |
| 404 画面からの遷移 | `history.replaceState` 相当で履歴を汚さず戻る（戻るボタンで 404 を踏まない） |
| 戻り先の `index.html` が無い | 遷移を 1 回で打ち切り「自動で戻れませんでした」＋手動リンク |
| サブパス配信（`/repo/nope`） | `/repo/index.html` を選んで着地 |

## 8. 実行履歴と比較

実行するたびに結果が記録され、**このブラウザ内（localStorage）にだけ** 保存されます。外部送信はしません。実測モードのみが対象で、シミュレーションは記録しません。

### 8.1 保存される内容

| 項目 | 内容 |
| --- | --- |
| 日時 | 実行開始時刻（ローカル時刻で表示） |
| ホスト / URL | 対象オリジンと完全な URL |
| p50 / p95 / 最大 | その回の遅延 |
| 送信 / 成功 / 失敗 | 件数と失敗率 |
| 間隔 / 回数 / 所要時間 | 実行条件 |

上限 200 件。古いものから自動で捨てます。「履歴を消す」で全消去できます。

### 8.2 3 つの分け方

ツールバーの「まとめ方」で切り替えます。

| まとめ方 | 動き | 用途 |
| --- | --- | --- |
| **N 回ごとに分ける** | 新しい順に 5 / 10 / 20 / 50 件ずつ束ねる | 「直近 10 回」と「その前の 10 回」を比べる |
| **日時で分ける** | 今日 / 直近 7 日 / 直近 30 日 / それ以前 | 時間が近い測定と遠い測定を分ける |
| **ホストで分ける** | 対象オリジンごと | 別ホストの結果を混ぜない |
| まとめない | フラットに並べる | 全体を眺める |

さらに「ホスト」の絞り込みで、特定のオリジンだけに絞れます（`まとめ方 = ホスト` と併用可）。

各グループの見出しには、その束の **件数・p50 中央値・p95 中央値・失敗率** が出ます。束単位の傾向を先に見て、必要なら行を開いて個別の数値を見る、という順で読めます。

### 8.3 比較のしかた

上の一覧から **2 行をクリック**すると、下に差分表が出ます。

* 古い方が「基準」、新しい方が「比較」として自動で並びます
* p50 / p95 / 最大 / 失敗率の 4 行について、絶対差（ms, pt）と相対差（%）を表示
* 緑＝改善、赤＝悪化、灰＝ほぼ同じ（p50 の変化が ±5% 以内）
* 実行直後は、**同じホストの前回結果**が自動で選ばれます

対象ホストが違う 2 件を選ぶと、経路が違うため単純比較できない旨の警告が出ます。数字は出しますが、判断材料としては扱わないでください。

### 8.4 注意点

* 履歴はブラウザごと・オリジンごとに独立です。別のブラウザやシークレットウィンドウには引き継がれません。
* `localStorage` を消す（サイト データの削除）と履歴も消えます。
* ページを再読み込みすると **測定対象は同梱ファイルに戻ります**（履歴は残ります）。続けて同じ対象を測る場合は URL を再入力してください。
* プライベートモードなど保存できない環境では、記録は静かに失敗し、計測自体は続行します。

## 9. 運用上の注意

* 第三者のサーバーに負荷をかける行為は、日本では不正アクセス禁止法や偽計業務妨害の評価対象になり得ます。国によってはコンピュータ・ミスユース法違反です。**許可を得た対象だけ** に使ってください。
* このページを公開ホストに置く場合、誰でも「自分のサイト」を測れてしまいます。上限が低いので実害は小さいですが、身内用なら **アクセス制限（Basic 認証や Cloudflare Access）** をかけるのが無難です。
* より本格的な計測が必要なら、k6 / wrk / ab などサーバー側から実行するツールの方が正確です。ブラウザ経由の計測は CORS と mixed content の制約を受けます。
